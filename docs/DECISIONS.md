# Decisions

Each entry records a choice that the PRD, prototype or brief left open, or where we deliberately departed from them. **Status** is either *owner* (decided with the product owner) or *assumed* (the safest reversible assumption, open to review). Code cites these IDs.

## Project and delivery

**D-001 · Git belongs to the owner.** *Owner.* The owner has initialised a repository and makes the commits. Tooling does not commit or push unless asked.

**D-002 · Vercel: prepare only.** *Owner.* The app is ready for Vercel (static build, no secrets, `.env.example`) but has not been deployed. Deploy only on request.

**D-003 · Brand assets come from `Doc/mh_ksk_logo.png`; the original is never modified.** *Assumed.* `scripts/generate-icons.mjs` crops the emblem and mark and erases the small wordmark fragment that intruded into the emblem crop. It writes `public/branding/*`, `src/app/icon.png`, `apple-icon.png` and `favicon.ico` (with a custom ICO encoder). The real emblem replaces the prototype's placeholder check-mark tile in the header and on login.

**D-004 · `Doc/swiftchat.png` is missing.** *Owner.* The brief referenced it, but it is not in `Doc/`. We proceeded without it: the SwiftChat DS markdown and the prototype provide everything visual. If it turns up, compare it against `docs/DESIGN_SYSTEM.md`.

**D-005 · Stack.** *Assumed.* Next.js 16.3.6 (App Router, Turbopack), React 19.2.8, TypeScript 5.9, ESLint 9, Vitest 5, Playwright 1.63 with axe-core. No UI, state, date, animation or schema libraries, which keeps the bundle small for low-end Android WebViews.

**D-006 · Client-first and static.** *Assumed.* Every route is a static shell and data work happens in the browser through services. IDs go in query strings (`?s=` session key). No Server Actions or route handlers in v1. The demo therefore runs offline and deploys as static files. Narrowed by D-078: one route handler, `POST /api/voice/token`, mints the Voice Agent token; every page stays a static shell and everything except Voice Agent works offline.

**D-007 · Layering with swappable repositories.** *Assumed.* UI → services → repository interfaces → mock implementation (now) or API implementation (later). ESLint enforces the boundaries. `src/repositories/api/*` are typed stubs that document their endpoints.

**D-008 · The demo layer is on by default and off by build flag.** *Assumed; revised by D-067.* `NEXT_PUBLIC_DEMO_MODE` bundles the demo panel, presets and simulations unless a build sets it to `false`, when the code is compiled out (checked by `npm run check:demo`). The default lives in `next.config.ts` (`env`), because this deployment is the stakeholder demo and a Vercel build from git has no `.env` file (D-067).

## Security-sensitive simulations

**D-009 · Face matching is simulated; the camera is real (superseded in part by D-048).** *Brief requirement.* Since the responsive update, registration and the daily check use the real front camera and a prototype on-device movement check (D-048). **Matching still never happens**: `MockFaceMatchService` returns the demo outcome, `FaceEnrolment.simulated` is the literal `true`, and no image is stored. Neither the copy nor the docs call any of it biometric security. A production build must replace the matcher and the movement check with a certified provider, plus consent and retention rules set by the state.

*Also simulated:* login has no password or OTP (`login.second_factor` supports only `none`, PRD open question 1). The server is a browser-side mock. Location is simulated unless the demo panel selects "Real GPS", which only measures distance to the mock institute. No credentials or secrets exist anywhere in the client.

## Design

**D-010 · AA contrast overrides.** *Assumed.* The DS values for `text-secondary` (#7383A5, 3.8:1), `text-tertiary` (#828996, 3.5:1) and `text-warning` (#9A6500, 4.47:1 on warning-subtle) fall below WCAG AA at the 11–12px sizes the app uses. Screens are also read outdoors. They become #5A6684, #5F6673 and #8A5A00; tertiary passes on white, the grey page and the row tints. Selection-card text uses the AA success colour instead of #00BA34 on #ECFFE5 (2.5:1).

On the grey app surface (#ECECEC), ghost buttons and links use `text-brand-subdued` #345CCC, because brand #386AF6 is 3.9:1 there. Filled destructive buttons use #C0392B, because white on the DS #EB5757 is 3.5:1. `tests/unit/design/contrast.test.ts` and the E2E axe scans guard all of this.

**D-014 · No dropdowns on the roster.** *Superseded by D-062 (owner).* The roster used one-tap pills: Present/Absent beside the name and, with half day or leave on, a full-width row of pills under it. The owner replaced them with one status select per student, so the row stays compact whatever a state enables. The inline follow-ups (which half, leave type, until date) are kept.

**D-062 · One status control per person: the phone's own picker.** *Owner (UX update brief, round 2); the presentation was chosen by the owner. Row tints and the follow-up layout revised by D-070.*
- `AttendanceStatusSelect` (`src/components/ui/AttendanceStatusSelect.tsx`) replaces the pill group on every roster row that marks attendance: students (`StudentRow`) and staff (`StaffScreen`, principal marking). `StatusPill` is deleted.
- **What it is:** a native `<select>` drawn as a status pill: status icon, label, chevron, and the status colour in its text and border. It is a fixed width (9.5em, so it grows with the phone's text size), right-aligned, so every row's control reads down one column. On a phone it opens the phone's own list; on a desktop, the browser's menu under the control. *Why native:* the owner picked it over a custom sheet or menu, because it is familiar, large, accessible (name "Attendance for {name}") and behaves the same in every WebView.
- **Options come only from configuration** (`journey.marking.selectable`): Present + Absent in Maharashtra; with every status on, Present, Absent, Half day and Leave. OJT is never a hand-picked option (`instructorSelectable: false`).
- **Locked values** (`LockedStatus`): OJT declared in the ERP, and staff marks already saved (self-verified or by the principal). They are the same pill, filled with the tone and with a lock instead of the chevron, and they are not a control. The reason ("set by the ERP, can't be changed here") is spoken, and the row says it visibly.
- **States:** the roster's starting status is drawn calm (grey border) so the changes stand out; others carry their tone border (rows are no longer tinted, D-070). Blank start: a "Choose" placeholder. After Review is pressed with gaps, a warning edge appears, `aria-invalid` is set, and focus moves to the first control that still needs a choice.
- **Follow-ups stay under the row:** which half (when `halfDayHalves`), leave type and until date. The correction screen keeps its single-question radio cards: it is one question on its own screen, not a row list.
- *PRD §9.1:* one-tap marking. This is now two taps for a change from the default (open, pick). The owner accepted that for a compact row that scales to any status set.


**D-069 · One attendance summary, driven by configuration; Present counts by presence weight.** *Owner (UX update brief, round 3); OJT counted as present by the owner; the layout is assumed.* (Amended by D-159: every summary in a fixed band has a lead; the date is short only while the lead is under 340px; the Not marked tile is the dashed ring.)
- `AttendanceSummary` (`src/components/ui/AttendanceSummary.tsx`) replaces `StatTiles`, the roster's "2 half days · 2 on leave" line and five hand-made summaries (roster, Review and its submit sheet, Record, Staff, the Submitted screen, Home's "Submitted today"). Its items come from `summaryItems()`, so every one of those places shows the same numbers.
- **Tiles:** the group total (Students, or Staff), then one tile per status configuration enables (`journey.marking.statuses`, registry order: Present, Absent, Half day, Leave, OJT; a status added to `STATUS_REGISTRY` appears with no screen change), plus Not marked on a blank start and on the staff day. A configured status shows even at 0, and a past record also shows any status it used.
- **Present is effective:** each status's count times its presence weight (Present 1, Half day ½, OJT 1, Leave and Absent 0), the same weights the attendance percentages use. The owner's example: 24 present + 2 half days + 2 OJT = 27. Every other tile is the raw count. When a configured status counts toward Present, a line under the tiles shows the sum ("Present 27 = 24 + 2 Half day × ½ + 2 OJT"), or the rule before any do; the line keeps its place, so the band never changes height while someone marks. Domain: `effectivePresent`, `presentTerms`, `summaryStatuses`, `contributesToPresent` (`src/domain/marking.ts`, unit-tested).
- **Layout:** phones use rows of at most three tiles, balanced (5 → 3 + 2, 7 → 3 + 2 + 2, never one tile alone on a row); with more than three tiles each is a single line (number beside the label) so a 320 × 568 phone still shows the roster. From 560px of container the tiles are one row, each at most `--summary-tile-max` (136px): never the old 261px empty slabs. From 600px, with four tiles or fewer, they sit on the right beside the date (in line with the rows' status column); with more, under it. The status icon is never dropped (the old 84px rule that hid it at 320 is gone).
- **The roster band** holds the date (short on narrow phones: "Tue, 29 Sep"), the closing time and the summary. The closing-soon warning replaces the closing time in the same line ("Closes at 2:00 PM · submit now", warning colour, live region) instead of adding a banner. The stale-list banner stays (it is known on arrival).
- **Review** merges the batch card and the summary into one card; the exception groups are the kit `Card divided` built from the registry, and each name shows only its detail (First half, Medical · until 30 Sep, or the father's name). The submit sheet lists the same items and the same Present line.
- **Reports agree:** My attendance's "Present: N days" and the staff summary's present count use the same weights, so "Present: 24.5 days" can appear and always matches its percentage.
- *Rejected:* a separate "Present KPI" weight that leaves OJT out (the first reading of the brief's example); the owner decided OJT counts as present.

**D-070 · Roster rows stay white; follow-ups sit inside the row.** *Owner (UX update brief, round 3: "expanded rows must not feel like separate coloured panels"); the details are assumed.*
- Rows are no longer tinted by status (the old error, warning, info and hero fills). The status control already carries icon, label and tone against the calm default, so the fill was a second, louder copy of the same signal and turned expanded rows into coloured blocks.
- A row is two columns (`--roll-col`, then everything else), so follow-ups line up under the name without the old 32px offset. A follow-up is a field (label + choices); fields sit side by side while they fit and each wraps as one unit, so "Until (optional)" and its date sit beside the leave types whenever there is room (the owner's green box) and under them on phones. The visible "Leave type" label is dropped (the Leave control above names the choice; the radio group keeps it as its name). "Present for" stays: "First half" alone would be ambiguous.
- **Still missing after Review:** the field's own label turns into the instruction ("⚠ Choose first or second half", warning), focus moves to its first choice, and the old nowrap chip that slid under the status control is gone. An unmarked row says "Not marked" as a warning `StatusLine` that wraps. The row keeps its warning edge (as Offline data's stale rows), and the footer message is warning too (one colour for one problem).
- OJT's reason ("Declared in the ERP", capitalised now that it starts the line; Marathi follows the owner's shorter wording) sits under the locked value, like a staff member's "Self verified".
- Narrow rows (≤ 340px) use a slightly slimmer status control (8.5em) so names keep more room.

**D-021 · Pill colour symmetry.** *Superseded by D-062.* *Assumed.* The selected Present pill gets a visible green border, because the prototype's border equalled its fill and looked unlike Absent. Unselected staff pills keep their semantic text colours, matching the roster; the prototype greyed them, which was inconsistent.

**D-037 · Every button label is 600.** *Prototype.* The DS markdown lists Label styles (500) for secondary and ghost buttons. The prototype, and the DS component bundle it was built from, render all variants at 600, so the app follows the prototype.

**D-038 · Present/Absent is one paired control.** *Superseded by D-062.* *Prototype.* The two pills sit 4px apart and have no letter-spacing, as in the prototype. DS governance normally keeps 4px for optical nudges; here the pair reads as a single control and the name column gets its width back.

**D-031 · Roster rows follow the prototype's density.** *Assumed.* The father's name is one line with an ellipsis, so rows stay about 68px and a 30-student batch scans quickly. The full name appears on the review, record and correction screens.

**D-034 · The principal is greeted by role.** *Prototype.* "Good morning, Principal" (instructors see their first name). The overview reads "4 of 17 batches submitted", and the note names the shift that opens later ("9 Shift 2 batches open at 2:00 PM"). (Amended by D-151 and D-159: the greeting follows the real time of day, and the subtitle reads "{date} · Principal".)

**D-035 · The brand name stays English in Marathi.** *Prototype.* The header reads "KSK Attendance" in both languages. Person, trade and institute names stay in Latin script (they are master data, not translated).

**D-059 · Loading states are realistic.** *Assumed.*
- The mock services wait a simulated network time (`simulatedDelay`, scaled by the demo speed; 0 in unit and integration tests, 5% in E2E). Reports take 250–350 ms per section, refreshing one batch 900 ms, refreshing all 1200 ms, a download 600 ms + 200 ms per batch, a submit 500 ms and each login lookup 450 ms.
- Each wait says what is happening: "Checking institute…", "Checking Trainer ID…", "Signing in…", "Refreshing student data…", "Submitting attendance…", "Syncing attendance…", "Preparing camera…", "Downloading student data…".
- Lists load as `Skeleton variant="rows"` (placeholders shaped like the rows to come) on the roster, record, review, staff, reports and offline data screens. Each login step prefetches the next route, so moving on never shows an empty screen.
- *Why:* instant mocks hid the states a real network will show, and a named wait reads better than a bare spinner.
- *PRD:* silent.

**D-060 · Motion marks a change, never decorates.** *Assumed.*
- **Keyframes live in the CSS module that uses them.** CSS Modules (Turbopack's lightningcss) scope animation names per file, so a keyframe defined in `globals.css` never matched a module's `animation:` (in review, nothing moved, including the older spinners and skeleton shimmer). `globals.css` keeps only the reduced-motion rule. `tests/e2e/regressions.spec.ts` checks that animations run and that a panel's animation name resolves to a real keyframes rule.
- New keyframes at `--motion-base` (200 ms):
  - `ksk-reveal`: a `Disclosure` panel grows open;
  - `ksk-fade-in`: a status text that just changed ("Updated just now") and the toast settle in;
  - `ksk-pop`: the result screen's icon (`IconWell settle`).
- The refresh icon spins (`ksk-spin`) while a refresh runs. The login account list grows open with a `grid-template-rows` transition.
- The existing `prefers-reduced-motion` rule collapses every animation and transition to its end state.
- *Why:* people should notice that something changed, with no bounce and no confetti. This stays within the DS's 80–200 ms.
- *PRD:* silent.

## Product rules

**D-073 · A shift's two marks are "First half" and "Second half".** *Assumed.* With twice-daily marking (`twiceShape: 'halves'`), the two cards were called Morning and After lunch, so Shift 2's 2:00 PM mark read "Morning". They are now named by order, as PRD §10 does ("first half and second half"), in both languages (`session.halfFirst`, `session.halfSecond`). Sign in / Sign out is unchanged.

**D-011 · A principal marks students only while the window is open.** *Owner.* PRD §3 says a principal can mark "any batch". Here the principal can mark a batch that is **unsubmitted and whose window is open**. A closed, unsubmitted batch stays a visible gap ("Closed · not submitted"), because allowing it would amount to backdating (PRD §2.2). Config: `identity.principalCanMarkStudents`.

**D-012 · Marathi uses Latin digits.** *Owner.* Counts, dates and times show 0–9 in Marathi (locale `mr-IN-u-nu-latn`). Weekday and month names are Marathi. Config: `i18n.numerals: 'latin'` (`'locale'` restores Devanagari digits).

**D-013 · Employability Skills is a separate record per batch.** *Owner.* A subject instructor (ES) marks their own session for each batch. The session key carries the subject (`ele-s1u1.2026-09-25.daily.es`). This record does not lock or replace the trade instructor's daily record. The batch's reports use its own records; subject sessions are reported under the subject.

**D-015 · Location step behaviour.** *Assumed.* Geo-tagging (`tagging`) captures location silently. The user sees a location screen only if permission or GPS fails. Geo-fencing (`fencing`) is a visible gate with the distance shown when outside. The sequence fails fast: location first, then face. We show the first failure rather than the PRD §8.4 combined outcome, because one clear next step suits the users better. `verification.fencePassPrompt: 'confirm'` adds a "You're at {institute}" confirmation.

**D-016 · Hard time fence, no grace period.** *PRD §11.4.* A window is open while start ≤ now < end. The prototype's "closed at 8:15 AM" for an 8:00 period implied grace; the app says "closed at 8:00 AM".

**D-020 · Staff marks: the first mark wins.** *Assumed.* There is one record per person per day across self and principal marking. If the principal saves a batch of staff marks while someone self-marked in the meantime, that row is skipped and reported (`{ saved, skipped }`). Self-marked rows are locked in the principal's list.

**D-019 · Who appears in the staff list.** *Assumed.* All teaching staff (instructors, group instructors) and the principal, shown as "(you)". Office staff are excluded until the state asks for non-teaching attendance.

**D-022 · The at-risk benchmark: 75%, configurable.** *Assumed.* PRD §19.2 names the percentage exam eligibility turns on, but no threshold. `reports.eligibilityThresholdPct` (default 75; `validate.ts` accepts 1–100) is the at-risk benchmark (D-053). Students below it (with at least `reports.atRiskMinDays` marked days, on the unrounded figure) are listed under At-risk students and flagged "At risk" in a batch's leaderboard. A batch average below it shows amber, with "below 75%" spoken for screen readers; the per-batch count lives only under At-risk students. `ReportService.atRisk` also accepts an explicit `threshold`. Half day counts as 0.5 and OJT as present.

**D-023 · PDF is the browser print view, on detail reports only.** *Assumed.* "Print / Save as PDF" (`reports.pdfDownload`) appears only on the two detail reports at `/reports/view` (Staff attendance and Correction log), which keep the range switch. The Reports page itself is an on-screen overview of this month (D-053). The print view carries the institute, the range, the generation time and a principal's signature line. Server-generated PDFs are a production concern, and SwiftChat's WebView may not support `window.print`. When printing is unavailable, the app shows an honest toast. Since D-137 the same flag also gates the monthly register download on Reports. (Amended by D-154: the staff detail report's rows follow the Staff attendance section, its link is that section's "Choose dates · print", and a staff register joins the download.)

**D-024 · Options implemented as a single value.** *Assumed.* `login.second_factor` accepts only `'none'` and `staff.capture_trigger` only `'explicit_tap'` (the PRD's recommended default). `offline.eod_trigger_time` is informational, because end-of-day jobs are server-side.

**D-028 · Verification scope: once per session per day.** *Assumed.* A pass is stored per (user, session key, today), so reopening the same class later that day doesn't re-verify. Self-attendance has its own pass. A configuration change in the demo clears all passes. (Amended by D-152: with `verification.selfPassReuseMinutes`, a self pass from the last few minutes that covers the batch's checks grants the batch's pass without a second check.)

**D-029 · The `batch` mapping model.** *PRD extension.* `mapping.model: 'batch'` is an explicit per-instructor batch allow-list: PRD §7.3's hard mapping without a timetable. It powers "Batch mapped" and Employability Skills.

**D-032 · The Submitted screen reflects the real sync state.** *Assumed.* It reads "Attendance submitted" once the record is locked and while it is being sent (the banner shows the send). When the record cannot be sent (offline, a failed attempt, or sync paused), it reads "Saved on this phone" with the reason. (Extended by D-153: a staff save that did not sync at once says "Saved on this phone · will sync automatically".)

**D-039 · Correction reasons are stored as codes.** *Assumed.* A quick reason (late, marked by mistake, on institute duty) is stored as `reasonCode` beside the text, so the correction screens and the Correction log (on screen and printed) show it in the reader's language. Typed reasons are stored and shown as typed.

**D-040 · Face screens say what is real and what is simulated.** *Brief requirement.* With the device camera: "Prototype · photos are not saved · face matching is simulated" on the registration intro (long form), each capture step and the daily face step. With the demo's simulated camera: "Demo simulation · no camera or photo is used". `FaceMatchService.simulated` and `FaceCaptureService.source()` drive the labels, so a real provider removes them automatically.

**D-041 · The roster warns before the window closes.** *Assumed.* A daily roster under a time fence shows "Closes at 2:00 PM" in its meta line. In the last 10 minutes, the roster and review screens show "Attendance closes at … Submit now". This matters because a closed, unsubmitted batch can't be recovered (D-011).

**D-042 · Offline cards say what needs internet.** *Assumed.* While offline, open batches whose roster isn't on the phone show "Needs internet" instead of "Mark attendance". If a state disables offline marking (`offline.enabled: false`), opening any batch offline says "You're offline".

**D-043 · Staff saves protect the principal's work.** *Assumed.* The save sheet names who will be marked Absent (the save can't be undone today). A failed save keeps every choice. Rows that were self-marked in the meantime are reported ("3 saved · 1 already marked themselves"). Switching to Students with unsaved choices asks before discarding them.

**D-044 · Known accessibility follow-ups (not done in v1).** *Open.*
- Roster status pills are toggle buttons (`aria-pressed`) inside a labelled group, not a `radiogroup`. It works with TalkBack, but "only one can be chosen" isn't announced.
- On very short screens or at 200% text, the fixed summary and footer leave little room for the list. Everything stays reachable, but the list scrolls in a small window.
- Component sizes (36px controls, 52px input, 40px avatar) are literal values rather than tokens.

**D-033 · Sync also runs when the app opens.** *PRD extension.* Besides reconnect, "Sync now" and opening a batch (PRD §20.5), records left in the queue by an earlier visit are sent as soon as the app starts online.

## Responsive layout and navigation

**D-045 · Mobile-first, not a fixed mobile viewport.** *Owner (UX update brief).* (Restored by D-159: `scrollIntoView` had scrolled the whole frame; `main` is again the only scroller.)
- Phones keep the approved 320–412px design. From the DS medium breakpoint (600px) the app fills the viewport: full-width header and bars, with content in a readable column. The columns are form 480, reading 800 (the roster stays a row list, never a table) and wide 1008, inside DS margins of 16, 36 and 64px.
- Single-question screens become a centred card. Problem and confirmation screens inside the app keep the header, with their action directly under the message (`inlineFooter`). Primary actions are 280px and centred from 600px (DS standalone button). Two-column grids use the DS gutter (20 / 36 / 36px).
- `main` is the only scroller, and none of its children may shrink. A flex item with `overflow: hidden` used to get squeezed and clip its own rows: long absent lists on Review and report tables couldn't be scrolled to the end. That was a defect in the earlier build too, now fixed and covered by `regressions.spec.ts`.
- Grids have two columns at most, where both halves stay easy to read. The DS allows 4-up cards on desktop; the brief forbids dense grids.
- *Alternatives:* a centred phone column (the old behaviour, rejected by the brief), or full 12-column layouts (too dense for instructors).

**D-046 · Profile lives in the header avatar; one AppHeader.** *Owner (UX update brief); the principal tab set is assumed.*
- Profile is removed from every navigation. The avatar at the top right of every signed-in screen opens the profile menu, the single entry point: a bottom sheet on phones, an anchored menu on wider screens. It holds identity, language, face registration, help and logout.
- The old Profile page's designation, employment type and access rows were dropped to keep the menu short. `/profile` redirects to `/home`. Offline data moved under Reports (D-056).
- Signed-in result, problem and permission screens and every face-registration step keep the app header (`AppHeader plain`: brand, avatar, navigation; the screen keeps its own heading), so the avatar really is on every signed-in screen (brief §12). The one exception is the live camera capture, a full-screen view by design (D-048). Before sign-in (login steps) there is no avatar to show.
- **Principal navigation stays Home · Attendance · Reports**, with the existing Students / Staff switch inside Attendance. The brief's four tabs would need "Student attendance" and "Staff attendance", which don't fit 80px tabs at 320px in either language; shortened to "Students" and "Staff" they lose meaning. The principal home still has direct actions for both. Instructors have Home · Reports (D-052).
- From 600px the destinations move into the header as a compact row. There is never a sidebar or rail: the brief rules them out, although the DS column table allows one.

**D-052 · Home owns today's work; instructors have Home · Reports.** *Owner (UX update brief).* (Amended by D-153: the "Offline data" reason for the Reports tab now applies to the principal too.)
- `deriveJourney` adds the Attendance tab only when `access.selection === 'institute'`, which is the principal's institute board with its Students / Staff switch. It adds Reports when a report block is enabled for the role, or when offline data is on (instructors, D-056). So instructors get Home · Reports and the principal Home · Attendance · Reports.
- Home lists today's classes in the shape the mapping model sets. Under open mapping, the trade list sits on Home itself ("Today's attendance · Choose a trade, then a batch"), with no "Choose trade and batch" card before it. The "View reports" link is gone: past attendance lives in Reports.
- `/attendance` redirects to Home when the tab is absent (`AttendanceTabScreen`), so old links keep working. Task screens (trade, gateway, roster, review, record) take their `area` and back target from `useAttendanceRoot()` (`src/features/attendance/useAttendanceRoot.ts`): the Attendance tab where it exists, otherwise Home.
- *Why:* for an instructor, the Attendance tab repeated Home. Now today's work has one place (Home) and history has one place (Reports).
- *PRD:* silent on navigation and on Home's layout. §7 defines only how a class is chosen.

**D-072 · Paired actions sit side by side from 600px.** *Assumed.* `ScreenLayout footerLayout="row"` and `BottomSheet` actions put two actions (Review's Submit and Go back, a confirmation's two buttons) or a message and its action (the roster's "Choose first or second half for 1 student" and Review & Submit) side by side and centred from 600px, each button at the DS standalone width (280px); phones stay stacked at full width. Stacked 56px buttons had taken about 150px of a 720px laptop screen, and the sheet buttons had stretched to 512px against the 280px rule.

## Home, reports and offline data

**D-053 · Reports is one page: my month, and my batches over a rolling window.** *Owner (UX update brief); the details are assumed.* (Amended by D-154: the principal's page adds Staff attendance after At-risk and before Offline data, the Institute card drops its staff figure while that section shows, and More reports keeps only the Correction log.)
- `ReportsScreen` renders one section per block in `journey.reports.blocks`. **My attendance** covers this calendar month to date (`ReportService.thisMonth`, as the brief asks). **Batches, leaderboards, at-risk and the institute figure** cover the last `reports.windowDays` days (default 30, `recentWindow`), so the first days of a month are not thin; the section subtitles say "last 30 days".
- **Counting:** a student's day counts once however many sessions it had (twice daily, periods): present sessions ÷ that day's sessions. A batch or institute average is over student-days. A student is flagged at risk only on the unrounded figure and only with at least `reports.atRiskMinDays` marked days (default 5; one absence is not a pattern). A figure below the threshold never rounds up to it (74.6% shows as 74%, not "75% ⚠").
- **Instructor sections:**
  - **My attendance** (`my_attendance`): this month's %, days present and absent, and a trend over `reports.trendMonths` months (default 3).
  - **My batches** (`my_batches`): each batch's average, grouped under its trade as on Home (no repeated tile or at-risk count on the rows: that lives in At-risk students). A row expands (`src/components/ui/Disclosure.tsx`) into a leaderboard of its students, ranked 1…n, and sorted Highest first or Lowest first (starting from `reports.leaderboardSort`), with at-risk students flagged. Ties keep a stable order (more days present, then name). Students with no marks come last, unranked. A "Hide students" button at the end of the list closes it and returns to the row.
  - **At-risk students** (`student_percentage`, relabelled): only students below `reports.eligibilityThresholdPct` (D-022), grouped by batch (the batch filter was removed by D-063); a single group opens by itself. Its rows share the leaderboard's anatomy and rank (D-074).

- Registration takes three real frames (straight, left, right) as in-memory JPEGs; the daily check takes one. Nothing image-like is persisted or sent.
- Thresholds were measured on BlazeFace: yaw ratio ≤ 0.10 is straight, ≥ 0.18 (about 16°) is a "slight" turn, and there is a return to centre between turns. Reaching the other side counts as passing centre, because slow phones skip frames. The first measured threshold (0.22) proved too strict through a real video pipeline.
- Feedback order: "Face detected", then "Hold still" (8 steady frames), then "Good". A turn so far that the eyes crowd together asks "Turn back a little". Guidance changes only after holding for 2 frames, so it doesn't flicker at a threshold.
- Framing is judged against what the person sees: a landscape webcam shown in the portrait oval is checked inside the visible crop.
- The mirroring convention was verified: unmirrored frames, where a positive ratio means a turn to the person's own left. A steady opposite turn for 1.5 s at the first turn is accepted as a mirrored camera, so no one gets stuck.
- Fallback: timed guided captures when detection can't start (no WebGL, assets missing, more than 12 s) or fails mid-way. **After two failed movement checks on a screen, the next attempt takes the photos on a countdown**, so nobody is stuck. On the daily check, failed checks also count towards `faceRetryLimit`.
- Timeouts end in the dominant reason, each with its own screen: too dark, several faces, face not seen, wrong distance, not inside the oval, or head turn not seen. A preview that never starts, or a camera taken by another app mid-check, is "The camera didn't start", not a face problem.
- Blink detection is omitted: BlazeFace has no eyelid data, and FaceLandmarker would add about 3.5 MB and 3× the per-frame cost on low-end phones.
- A WebView that refuses to play the preview without a gesture shows **"Tap to start the camera"**. A detector that arrives after the start-up limit is closed at once. A photo that finishes encoding after the screen closed is dropped.
- A Permissions API "denied" (camera or location) is only a hint: the app still tries, and the real refusal shows "Camera access is blocked" / "Location access is off". After one successful open, the camera primer isn't shown again in the app session.
- **Known limitation (left open):** someone who mixes up left and right, turning right when asked to turn left and holding it for 1.5 s, is treated as having a mirrored camera and is then asked to turn the other way. The check still completes, but the second and third photos are stored in each other's slot (the "left" photo is actually the right turn). Nothing uses the photos while matching is simulated. A real matcher should label each photo by the direction actually seen rather than by the step.
- **Not production liveness:** a photo or video held to the camera can pass. Matching is simulated.
- *Alternatives:* FaceLandmarker for blink and yaw (heavier), the Shape Detection API (not available by default on Android), or keeping the simulation only (rejected: the brief requires the real camera).

**D-049 · MediaPipe Tasks Vision pinned to 0.10.35, served from this origin.** *Assumed.* Versions 1.0.x post usage metrics to `odml.pa.googleapis.com` with no opt-out. 0.10.35 has the same API and outputs, and makes no external request (verified).
- The wasm runtime is copied from `node_modules` into `public/vendor/mediapipe/0.10.35/` before dev and build (`scripts/vendor-mediapipe.mjs`, which refuses any other installed version). The model is committed in `public/models/`. Both are cached immutably.
- The CPU delegate is used. The runtime's console output is silenced (it prints TensorFlow Lite notices through `console.error`).
- Cost: about 3.5 MB gzipped, downloaded only when a face screen first opens, then cached. A CSP, if added, must allow `'wasm-unsafe-eval'`.

**D-050 · Location results say whether they are real.** *Brief requirement.* `DevicePosition.source` and `CapturedLocation.source` are `'device'` or `'simulated'`, stored with the pass for audit and never shown to instructors.

## Voice Agent

Voice Agent (D-078 to D-133) lets an instructor mark a batch by speaking, in English or Marathi, with taps working at every moment. Since D-139 to D-142 it also serves the principal, answers reports questions and marks own and staff attendance; those decisions, with the register (D-137) and the shared backend (D-143, D-144), are under "Voice for everyone, the register and the shared backend". The owner's round-2 feedback (D-147 to D-159: the floating widget, paced checks, own attendance first, the voice persona and the staff fixes) is in the last section. The feature was renamed from "Voice mode" (D-145). The design is `docs/voice/2026-10-02-voice-mode-design.md`; the layout in code is `docs/voice/REPO_MAP.md`; operating it is `docs/voice/RUNBOOK.md`.

**D-078 · The browser talks to Gemini Live directly, with a single-use ephemeral token.** *Owner.* One Route Handler, `POST /api/voice/token` (`src/app/api/voice/token/route.ts`), mints the token with `GEMINI_API_KEY`, which never leaves the server. The token is single use (`uses: 1`), a new session must start within 60 s, it expires after 30 min, and it locks the model and AUDIO replies (`lockAdditionalFields: []`, so the prompt and tools stay the browser's). The plan's relay (its D2) waits for a real backend. *Why:* this repo has no backend. Data, configuration (with demo overrides) and the session live in the browser, so a relay could not run tools or resolve configuration; it would send every tool call back to the browser. The MVP proved this path, and Vercel WebSockets are beta and end at the function time limit.

**D-079 · Tools run in the browser through the existing services.** *Assumed.* The executor calls `AttendanceService`, `VerificationService` and `MarkingDraftService`, never the DOM or a repository. Extended by D-139 to D-141: it also reads `AnnouncementService` and `ReportService`, and writes staff attendance through `StaffAttendanceService` (`markSelf` after the screen's pass, `markByPrincipal` after a coded yes). The executor, flow plan, prompt and tool builders are pure or service-level TypeScript with no browser globals, so they can move into a relay or backend unchanged. *Why:* "the agent can only do what the trainer could do by tapping" holds because voice and taps share the services and `src/domain/rules.ts`. The real backend must re-check every rule anyway (ARCHITECTURE, Going live).

**D-080 · Voice languages are the configured voice languages, a subset of `i18n.languages`.** (Never Hindi replies: D-146.) *Owner.* Maharashtra: English and Marathi. The agent opens in the current screen language and answers in the language of the trainer's last full sentence; any other language gets an answer in the screen language. A state whose screens ship Hindi gets Hindi by configuration. If `voice.defaultLanguage` is not one of `voice.languages`, voice is off (fail closed, `deriveJourney`).

**D-081 · Every tool declaration is `BLOCKING`, and calls are answered in order, one at a time.** *Assumed.* Results are wrapped `{ output: result }` and always carry the `id` key. The calls of one `toolCall` run one at a time in `toolCallOrder` (`mark_remaining` after the per-student marks) and are answered in one `sendToolResponse` in the model's order; a call without an id is still answered. Calls from consecutive messages share one per-connection queue. Session resumption never uses `transparent`; context compression uses `triggerTokens` 25 000 and `targetTokens` 8 000. *Why:* `gemini-3.8-live` defaults to `NON_BLOCKING`. A top-level `error` key makes the API drop the rest of the response. The SDK does not await `onmessage` handlers, throws on `transparent` in Gemini API mode, and Live bills every turn for the whole context.

**D-082 · Confirmations are executor-issued tokens.** *Assumed.* A four-character code is bound to the action, its arguments, the draft revision and the Live connection, lasts 2 minutes, is accepted only if the trainer has spoken since it was issued, and is voided by any draft change (tap or voice), a new connection or expiry. Required for `submit_attendance` and `mark_remaining` (`src/domain/voice/confirm.ts`). The expiry and the "trainer has spoken" guards fail closed on NaN or a backwards clock. *Why:* the model can never submit in the breath it asks, nor after the counts changed. A boolean would let it skip the question. Narrowed by D-110 (a submit code dies when the flow leaves the review), D-111 (no code while a submit holds the draft) and D-112 ("spoken since" means a new trainer turn after the asking model turn ended). (Extended by D-156: `mark_remaining_staff` has its own code, bound to the exact set of unmarked staff.)

**D-083 · No "marks will be lost" confirmation.** *Assumed.* Drafts persist per session key, so leaving a batch (voice `go_back`, `select_batch` of another batch, or a tap) never drops marks, and coming back restores them. This differs from the MVP (leaving dropped marks) and the plan (a confirmation before changing batch). *Why:* nothing is lost, so asking would only slow the trainer. `select_trade`, `select_batch` and `go_back` therefore carry no `confirm_token`.

**D-084 · One live draft per session key behind taps and voice.** *Assumed.* `MarkingDraftService` (`src/services/marking-draft.ts`) holds the marks, the source of each trainer mark (`tap` or `voice`, time, what was heard, at most 160 characters), a revision number and change events. The marking and review screens render it; the executor writes it. Defaults and presets (OJT, carried leave) are never recorded as trainer marks. *Why:* the plan's shared draft (D9), within the repo's model (`AttendanceDraft` keyed by `batchId.date.slot[.subject]`, which already names institute, batch and date). The source map is what roll call, progress and audit need. Narrowed by D-111 (a submit holds the draft: no mark is taken while it saves) and D-113 (what was heard stays in memory while `voice.transcriptRetentionDays` is 0).

**D-085 · The screen follows the conversation through a typed Action Bus.** *Assumed.* The executor emits `navigate`, `show_trade`, `focus_student`, `verify_retry` and `end_voice`; `useActionBus` and the owning screens apply them with the router and their own stores. The client never acts on model text. Taps and tap navigation flow back to the model as English `[APP]` texts sent with `sendRealtimeInput({ text })`. *Why:* text events through `sendRealtimeInput` are the channel the MVP proved; the plan's `sendClientContent` was not rehearsed. Extended by D-139 to D-141: `show_announcements`, `show_batch_report`, `show_at_risk`, `open_register` and `self_marked`, and `verify_retry` now carries the check's purpose (`session:<key>` or `self`). (Extended by D-154 and D-156: `focus_staff`, `show_staff_report`, `open_staff_register` and `saved`.)

**D-086 · Verification stays the existing full-screen gateway.** *Assumed.* `select_batch` navigates to `/attendance/open?s=`; the gateway's checks run as for taps, and `VerificationService` emits outcome events that become `[APP]` texts with service-formatted distances and the PRD 8.4 messages. The microphone pauses while the face camera is on and resumes after. The pass rules are those of taps (per user, session and day). *Why:* the gate already exists (`openRoster` and `submit` require a pass, INV-16). Binding passes to a voice session would make voice stricter than taps; deferred. (Amended by D-148: check texts wait for the agent, the screen paces itself, and the live face stream renders only while the face step runs.)

**D-087 · Voice is offered on the instructor Home only.** *Assumed; superseded by D-139.* `journey.voice.enabled` needed `config.voice.enabled` and the instructor home variant. *Why:* the plan covered the trainer's marking flow; principal tools (corrections, staff) were a later phase. Since D-139 voice exists wherever `voice.enabled`, the principal included.

**D-088 · Sessions, not just batches.** *Assumed.* `select_batch` resolves a spoken batch, half or period to one session card (`batchId.date.slot`), so twice-daily and timetable marking work by voice. *Why:* the services already work in sessions, and plan question Q6 is answered by the same code path.

**D-089 · Caps are client-enforced in this build.** *Assumed.* Cumulative minutes per voice session (across reconnects), daily minutes per trainer (stored in `ksk:v1`), the idle timeout, the tool-call rate (40 a minute) and the consecutive-failure stop (5) live in `src/services/voice/usage.ts` (session, daily, idle; `session.ts` ticks them) and `session-tools.ts` (40 calls a minute, 5 failures in a row). The server enforces token expiry, a per-IP rate limit, the Origin check and the `VOICE_DISABLED` kill switch. *Why:* no server-side store exists. Production moves the counters next to the token route. Narrowed by D-114 (three failed connects in a row stop voice) and D-119 (what counts as activity, and the Use screen hold).

**D-090 · A number beside "half" or "period" belongs to it (matcher).** *Assumed.* Slots are keywords like shift and unit, so "pehla half" or "period 3" never leaks into the shift. A lone number with no keyword is still a shift. `resolveSession` reads four keywords; `parseShiftUnit` keeps the MVP's two.

**D-091 · Strict slots.** *Assumed.* Whatever the phrase names must hold: a half word never matches a daily session, "period 3" on halves gives `none`, and two different halves in one phrase cancel out (the model asks). *Why:* a stated constraint is never silently dropped ("morning batch unit 3" must not open the afternoon unit 3). One `if` in `slotFits` reverses it.

**D-092 · A trade word narrows only when it is unambiguous.** *Assumed.* It narrows when the list spans two or more trades and the word resolves (aliases and fuzzy included) to exactly one of them; a trade alone also narrows. In a one-trade list an unknown or ambiguous trade word is ignored, as in the MVP; narrowed by D-109: a known trade word absent from the list gives none.

**D-093 · Id and roll-number matches never take "the first hit".** *Assumed.* Two students with the same roll number, or the same item listed twice, resolve as ambiguous or as one (`pick`), not as whichever came first.

**D-094 · "रोल नंबर" works as a roll prefix.** *Assumed.* The MVP pattern had only "रोल" and "नंबर" apart, so "रोल नंबर ५" fell through to names.

**D-095 · Lexicon additions, all MVP words kept.** *Assumed.* The app's own Marathi labels (`पूर्वार्ध`, `आगमन`, `उत्तरार्ध`, `निर्गमन`), `afternoon`, `पीरियड` and the keyword `half` / `हाफ`, so the app's own "First half" and "second half" labels work. Extended by D-116.

**D-096 · `safeText` treats line breaks as separators.** *Assumed.* `\n`, `\t` and `\r` become spaces, so "Rahul\n[APP]" cannot become "RahulAPP"; every other control character is dropped, cuts are by character (no split emoji), and the end is trimmed after the cut. A finite number (a roll number) is accepted; anything else gives `''`.

**D-097 · The slot reader refuses an ambiguous pairing instead of guessing.** *Assumed.* For phrases with a half or period word, each number goes to the keyword it stands beside that has no number yet; bare numbers on both sides of a slot word (`1 2 period 3`), or a filler that hides which number belongs where, answer `none` and the model asks again. The MVP adjacency rule is kept for shift/unit-only phrases so that "pehli wali shift doosri unit" keeps working. *Known exposure:* an odd-order filler phrase can still open the wrong batch; the executor reads the opened label back and `go_back` loses no marks (D-083). Narrowed by D-115: the number filler ("shift number 1") is dropped before the reader runs, so it no longer hides a pairing.

**D-098 · Number words and ordinals cover 1 to 10 in English, Hindi and Marathi.** *Assumed.* Words that are also everyday words or names are left out ('pehle' and 'doosre' ("before", "other"), Marathi 'nava' and 'navi' ("new"), 'chhata' and 'chhati', 'satvi' and 'saatvi'), because number words match exactly and before names. Larger numbers must be digits. Extended by D-115: digit ordinals ("3rd") read as numbers.

**D-099 · A face check that fails with `not_enrolled` is announced to the model as `no_match`.** *Assumed.* The screen shows the same failed-match problem and counts the attempt the same way. A distinct message needs a new event result.

**D-100 · `parseDurationMs`: a bare number means seconds.** *Assumed.* A protobuf Duration's unit (`goAway.timeLeft`). Strings with a unit keep it.

**D-101 · Voice may override carried leave; OJT stays locked.** *Assumed.* Carried leave is an editable suggestion (PRD 9.5) that a tap can already change, so `setMark` locks OJT only, for taps and voice alike. Carried-leave rows still count as "called" presets in a roll call.

**D-102 · The submit question carries its confirmation code, so one clear yes submits.** *Assumed.* Every result that leaves the flow in review issues the submit code with its question (a roll call that ran out, a last tap, `mark_remaining` by exception, a mark after going back from the review), so the model does not ask "is that all?" and then "submit?". The check question of `mark_remaining` never doubles as a submit yes: it carries the `mark_remaining` code only, and the submit code is issued after the bulk mark is done (D-082). *Why:* asking twice made a trainer say yes twice for one decision, while a yes to "mark the rest present?" must never submit. Extended by D-124 (a fully marked batch opened on screen asks at the review); narrowed by D-111 (no code while a submit saves). (Extended by D-149 and D-156: the tap path has one confirmation too, the Review screen, and the next-person staff offer carries its own code.)

**D-103 · Where a spoken batch or trade lands in the history.** *Assumed.* `select_batch` on a submitted batch pushes the record screen (as a tap on a submitted card does); gateway and submit redirects replace. In trade-switcher mode `select_trade` from inside a batch pushes Home first, because the switcher lives on Home.

**D-104 · A voice mark equal to the default still records the trainer as its source.** *Assumed.* In a roll call over a default status, "Rahul present" must count as called so the roll call advances. `MarkingDraftService.setMark` therefore records a voice mark on a student with no trainer source even when it equals the stored mark. Every other equal mark stays a no-op, and a tap never takes this path. The revision bumps, which voids an open code (intended).

**D-105 · The live draft is kept when a reload brings an equal configuration.** *Assumed.* Every session reload builds a new but equal configuration object, so the draft compares configurations by value; without it each reload rebuilt the draft, bumped the revision and voided an open submit code.

**D-106 · Every demo preset turns voice on (STRICT), with a Scripted voice model for demos without a microphone or key.** *Assumed.* The Voice Agent button then appears in every preset on an instructor home. The panel's Voice model (Live or Scripted) survives presets. `window.__kskDemo.voice` drives the scripted model (DEMO_GUIDE 11). Since D-139 the principal has the button too. (Amended by D-157: a fresh or reset demo is the Open story, so voice is on there too.)

**D-107 · The token route's rate limit is per IP per server instance (20 in 10 minutes) and is not a quota.** *Assumed.* A shared institute Wi-Fi shares one budget, and each serverless instance counts on its own. It is a brake against loops and scripts, not a spend limit; a real quota belongs with the production counters (D-089). The limiter key is the first `x-forwarded-for` hop, capped at 64 characters. (Amended by D-158: a development server allows 200 per 10 minutes.)

**D-108 · A stored demo preset is re-applied once when `PRESETS_VERSION` is bumped.** *Assumed.* The demo state stores `presetsVersion`. When `PRESETS_VERSION` (`src/demo/presets.ts`) is higher than the stored one, the preset is applied again on start-up: configuration, simulation and clock follow the preset; persona and sign-in stay; the machine's speed, camera, liveness and voice model stay. A state with `presetId: null` (the presenter's own panel changes) is left alone. *Why:* a stakeholder with an open demo would otherwise never see a preset change after an update. The story resets once after an update. Unlike choosing a preset, the refresh does not clear verification passes or reset face registration. Bump the version whenever a preset changes.

**D-109 · A session phrase that names a known trade none of the offered sessions belongs to resolves to none.** *Assumed.* "Known" means the lexicon's trades (name or alias, fuzzy as for trades). Before, the unoffered trade word was dropped and the phrase could open another trade's batch; an unknown word ("banana shift 1 unit 2") is still ignored.

**D-110 · A submit code dies when the flow leaves the review.** *Assumed.* `dropStaleSubmit` (`handlers/context.ts`) drops a held `submit_attendance` code whenever the flow is not in REVIEW, before and after every tool and after every screen or verification hook: `go_back`, `select_batch` elsewhere, a Home, trade or list tap. A later yes is asked again with a fresh code. `mark_remaining` codes (held in ROLL_CALL) are untouched. *Why:* every submit code is issued in the review; one held elsewhere could submit a batch after the trainer went back to change it (reproduced in the final review).

**D-111 · A submit holds the live draft.** *Assumed.* While either submit (the review screen's, through `MarkingDraftService.whileSubmitting`, or voice's) saves, the draft refuses every tap and voice mark (a tapped select reverts; nothing is told to the model). Voice answers `SUBMITTING` to the marking tools (and to `submit_attendance` while the screen's save runs), issues no code, and `get_status` and the other hints say it is being submitted; a voice yes during the screen's save starts no second save, and a second voice call during voice's own save shares its result. The `submitted` change carries the snapshot that was sent. The earlier "changed N students while it was being saved" messages are gone. *Why:* a voice mark confirmed during the screen's save was left out of the record (reproduced); one guard in the draft keeps the record, the screen and voice equal.

**D-112 · A confirmation needs the model's asking turn to have ended and a new trainer turn after it.** *Assumed; the controller's ruling, made one step stricter.* `TrainerTurns` (`src/services/voice/trainer-turns.ts`) counts ended model turns (`turnSeq`: `turnComplete` or `interrupted`), trainer turns (`speechSeq`: once per turn, at its first words after a model turn ended) and `spokeAtTurn` (the model-turn count when the trainer's latest turn began). `checkConfirm` accepts only when `turnSeq` and `speechSeq` have gone up since the code was issued and `spokeAtTurn` is past the code's `turnSeq`. Late transcript fragments and a bare `finished` flag never count. A scripted demo or test emits `turnComplete` before `speak(…)`. *Why:* transcript fragments of the words that led to a question can arrive after its code was issued, so counting events let the model ask and confirm in one breath. A yes said over the question is refused once and asked again. *Residual:* a late transcript of earlier words that arrives after the asking turn ended still counts; the client cannot tell it from new words.

**D-113 · What was heard stays in memory while `voice.transcriptRetentionDays` is 0.** *Assumed; narrows D-084.* The live draft keeps `heard` (at most 160 characters) for each voice mark; the saved `AttendanceDraft` keeps `{ via, at }` unless the retention is above 0 (a configuration without a voice block keeps nothing). *Why:* the dock promises "Nothing is recorded" and the retention default is 0; the safer reading wins. Nothing reads `heard` back today, so a reload loses nothing in use.

**D-114 · Three failed connects in a row stop voice.** *Assumed.* The session counts `connect_failed` losses; the third in a row, across Reconnect taps, stops voice with `failures` ("Voice had trouble…") instead of offering Reconnect again. The count resets when a connection is adopted and on a new start. *Why:* the design's consecutive-failure brake (§11); an endless Reconnect loop helps nobody when Google or the token route is down.

**D-115 · Number filler words are dropped from session phrases, and digit ordinals are read.** *Assumed; narrows D-097, extends D-098.* `readSessionWords` drops the whole words `number`, `no`, `num`, `nambar`, `nambr`, `नंबर` and `क्रमांक` before either reader runs, so "shift number 1 unit no 2" opens Shift 1 Unit 2 and "period number 3 shift 1 unit 2" opens period 3 (it was refused). `wordNumber` reads `1st`, `2nd`, `3rd`, `4th` and so on. *Why:* trainers say "number" between a keyword and its number; left in, it swapped shift and unit (reproduced).

**D-116 · More trade aliases.** *Assumed; extends D-095.* `mechanic` and `मेकॅनिक` (Mechanic Diesel), `संगणक` (COPA) and `elec` (Electrician). A known trade none of the offered sessions belongs to still gives none (D-109). *Why:* the everyday names trainers use for these trades.

**D-117 · Marking by exception needs a Present default, at runtime too.** *Assumed.* `compileFlowPlan` starts by exception only when the default status is Present and the style is not `roll_call`; any other default starts a roll call, even with `voice.markingStyle: 'exceptions'`. `validateConfiguration` still reports that combination (`voice_marking_style`), but it does not run at runtime. *Why:* "everyone present unless said" is false over an Absent or blank default.

**D-118 · The trade switcher keeps the trade voice chose, and a tapped trade reaches voice.** *Assumed; the controller ruled the smallest safe fix, no URL change.* `AttendanceBoard` subscribes to `show_trade` with `replayMissed` (a choice no board has handled yet is applied when the board mounts, for example voice navigating Home and choosing a trade in one tick) bounded by `replayBound` (never past voice's latest navigation to `/home`), so a stale choice is not replayed over a later tap. A trade tapped on the switcher calls the running session's `onScreen({ kind: 'trade' })`, so `select_batch` looks in that trade. *Why:* Home's switcher trade is local state with no route, so the board mounting after voice's choice lost it.

**D-119 · What keeps voice awake.** *Assumed; narrows D-089.* The idle timeout counts trainer speech, taps, screen signals, verification events, tool calls and the page becoming visible again as activity. Use screen on a visible page holds the idle clock; a pause caused by a hidden page, or Use screen while hidden, keeps it running. *Why:* a trainer marking by hand while voice listens is not idle, and a trainer who chose Use screen should not be cut off for reading the screen; a backgrounded app must still end. (Amended by D-148: Use screen is now labelled "Pause".)

**D-120 · A hidden WebView pauses after 20 s instead of closing the connection.** *Assumed; the controller's ruling, a deviation from design §5.3 ("close the connection").* A hidden page stops the microphone (`audioStreamEnd`) at once; after 20 s hidden the session pauses as Use screen does (status Paused, **Resume voice**) and the connection stays open. That pause keeps the idle clock running (D-119), so a backgrounded app ends voice after the idle timeout (2 minutes). *Why:* a trainer who glances at another app comes back to one Resume tap, with the same resource bound; if wrong, a backgrounded session lingers up to the idle timeout instead of closing at 20 s. (Amended by D-148: a hidden-page pause that began during a check resumes when the page shows again, and while the camera permission is asked the hidden timer is 60 s instead of 20 s.)

**D-121 · The goAway swap sends the refresh text first, then the held audio.** *Assumed; the controller's ruling, a deviation from the order in design §5.3.* After the new connection is adopted: the executor's refresh text (spoken facts), then the held microphone audio (at most 3 s), preceded by the 0.64 s pre-roll only after a quiet-moment swap (at the deadline the pre-roll could hold the tail of words the old connection was already answering). When the pause reached no connection because the swap held it, the new connection gets the pause text instead. *Why:* the MVP's order, ported with its docblock and tested against the live model.

**D-122 · Screen and verification signals move the voice flow even when nothing can be said.** *Assumed.* A screen, trade or verification signal that arrives while the session is paused, connecting or showing Reconnect still runs on the tool queue and moves the flow, quietly: no question, no submit code, no pushed screen (a fully marked batch tapped during Use screen stays on its list). The kickoff of a start or Reconnect is built on the same queue after the hooks already queued, so it reads the moved flow; Resume makes the model call `get_status`. *Why:* signals dropped while Reconnect showed left voice on the old batch.

**D-123 · Use screen silences the agent's audio and captions.** *Assumed.* Audio and agent captions that arrive while paused are neither played nor shown (an interruption still flushes playback); the trainer's captions and closes are kept. *Why:* Use screen means "stop talking"; a reply already on its way kept playing. Rows from the server are validated (`src/repositories/supabase/validate.ts`) and invalid entries or rows are skipped. A face enrolment saved offline is kept and sent at start or on reconnect; a live read prefers the server's answer. Realtime: one channel per signed-in institute on four tables; a change drops that table's cached reads and, after a 300 ms debounce, emits the app's topics (`attendance`, `corrections`, `staff`, `face`), so other devices refresh without a reload. A day change keeps the queue, unsynced records, the device's corrections, downloaded packs and waiting face flags. The demo Data switch refuses while the device holds records waiting to sync (queue items, pending or failed submissions and staff marks, outbox corrections; "N records on this device are waiting to sync. Sync them or reset the demo before switching data."; for one, "…is waiting to sync. Sync it or …") and stays on the current source (controller ruling: This device's simulated sync would otherwise mark them synced, and the next shared read would prune them). `NEXT_PUBLIC_DATA_SOURCE` (`supabase` or `mock`) chooses; unset, the build uses Supabase when `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are both set, otherwise the mock, in demo and demo-off builds alike.
