# Testing

```bash
npm test            # Vitest: unit + integration (2,300+ tests, voice and Supabase included)
npm run e2e         # Playwright: builds with NEXT_PUBLIC_DATA_SOURCE=mock, serves on :3200 (or $E2E_PORT), runs every spec (111 tests in 22 specs)
npm run check       # lint + typecheck + test + build
npm run check:demo  # proves a demo-off build contains no demo code
npm run test:voice-live   # opt-in, real model: needs GEMINI_API_KEY in .env.development (never part of npm test or CI)
npm run voice:spike-token # opt-in spike: mint, connect, time to first audio
npm run voice:spike-voices # opt-in spike: 9 candidate voices x 2 lines (English, Marathi) with the persona, to WAV in os.tmpdir()/ksk-voice-spike
npm run test:supabase-live # opt-in, real Supabase project: test institute 99999 only (never part of npm test or CI)
npm run voice:ui-rehearsal -- <scenario.json> [--base <url>] # opt-in, macOS: speaks the trainer's lines into the real app and model
```

**`E2E_PORT`.** `playwright.config.ts` serves and tests on `Number(process.env.E2E_PORT ?? 3200)`, so several working copies can run the suite side by side: `E2E_PORT=3310 CI=1 npm run e2e`. With `CI=1` Playwright never reuses a server already on that port; without it, a server left running there (perhaps an older build) is reused. Free the port first if a previous run left one (`lsof -ti tcp:3310 | xargs kill`).

`.env.development` is git-ignored, so a clone has none: `cp .env.example .env.development`, then set `GEMINI_API_KEY=`. Without the file the three opt-in voice commands stop with "not found" (Node's `--env-file`); with the file but no key, `test:voice-live` skips.

`npm run test:supabase-live` reads `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` from `.env.development`, then `.env.development.local` (both git-ignored; the `.local` file wins, as in Next). Without them, or on a Node without `process.loadEnvFile` (before 20.12) and nothing set in the environment, the suite skips. Only the publishable key is used, never a secret key.

**Which data source the tests use.** `npm test` runs on the mock container, and the Supabase layer against an in-memory fake project (`tests/unit/supabase-fake.ts`). `npm run e2e` builds with `NEXT_PUBLIC_DATA_SOURCE=mock`, so it stays on the mock even when an env file names a project. Only `test:supabase-live` touches the real project.

## Spoken UI rehearsal (opt-in, macOS)

`npm run voice:ui-rehearsal -- <scenario.json> [--base <url>]` (`scripts/voice/ui-rehearsal.mjs`, D-158) hears a voice change end to end: the real app, the real Gemini model, and the trainer's lines spoken by macOS `say` into Chromium's fake microphone. It is not a test and never runs in `npm test`, `npm run e2e` or CI. Use it after a change to voice wording, pacing or the card, beside `test:voice-live` (which sends typed turns, not audio).

How it works:
- It renders every line with `say` (default voice `Rishi`, Indian English) into one 16 kHz WAV: `lead` seconds of silence for the greeting, then each line followed by its `gap`, then `tail`. Chromium plays that file as its microphone (`--use-file-for-fake-audio-capture`), starting when voice starts.
- It opens `/?preset=<preset>&voiceDebug=1`, applies `simulation` through the demo controller, switches to Marathi through the profile menu when `lang` is `mr`, and taps the Voice Agent button.
- It logs, with timestamps: every change of the card's status and text (and an open dialog's text), URL changes, the token route's status (never its body), the `[voice]` debug lines, console errors and page errors. Tokens, keys and the Live WebSocket URL are redacted from every line.
- It saves `log.txt` (the plan of who says what when, then the log), `mic.wav`, each line's `line-N.wav`, a screenshot every `shotEvery` seconds and `final.png` in `os.tmpdir()/ksk-voice-rehearsal/<name>` (or `out`).

It needs a Mac (it stops elsewhere) and a running server with `GEMINI_API_KEY`. The usual form is a production build on the mock data, served with the env file:

```bash
NEXT_PUBLIC_DATA_SOURCE=mock npm run build
node --env-file=.env.development ./node_modules/next/dist/bin/next start -p 3311
npm run voice:ui-rehearsal -- scripts/voice/rehearsals/self-first.json --base http://localhost:3311
```

`next dev` (Next 16) refuses `node --env-file=…`; `npm run dev` already reads `.env.development` from the project, and the default `--base` is `http://localhost:3000`. Each run spends Gemini usage, and on the Supabase source the persona's shared daily voice minutes. A page error is logged but does not fail the run (only a rehearsal that breaks off exits 1), so read the log.

Scenario (JSON): `{ "preset": "open", "lang": "en" | "mr", "viewport": [1280, 800], "voice": "Rishi", "lead": 9, "steps": [{ "say": "Electrician", "gap": 9, "voice": "Rishi" }], "tail": 10, "shotEvery": 3, "out": "<dir>", "base": "<url>", "simulation": { "camera": "simulated" } }`. Only `steps` is required. Chromium's fake camera shows no face, so a scenario that passes a face check sets `"simulation": { "camera": "simulated" }`.

**Voice E2E.** The shared fixture seeds the Scripted voice model and the simulated camera; `voice.spec.ts` plays the model with `window.__kskDemo.voice` (`toolCall`, `texts`, `emit`, `speak`, `denyMic`; `playing(on)` makes the scripted agent "speak" so `voice-pacing.spec.ts` can test the pacing, and `earcons()` lists the tones played). A confirmation needs `emit({ turnComplete: true })` before `speak(…)` (D-112). Drops, goAway swaps and Reconnect are covered by the session unit tests, not E2E; `tests/helpers/voice-view.ts` and `tests/helpers/app.ts` hold the shared helpers. The real Gemini path is covered only by `npm run test:voice-live`, and the real microphone and speaker by the owner's smoke test (`docs/voice/RUNBOOK.md`, Owner smoke test).

**Console must stay clean.** The shared fixture (`tests/e2e/fixtures.ts`) fails any test that logs a console error, a page error, or a React/Next warning. It also starts each test with simulations at 5% speed, so flows are fast but still pass through every state.

**Own attendance first in tests (D-152).** Maharashtra turns on `staff.selfBeforeStudents` and a 10-minute `verification.selfPassReuseMinutes`, and the default persona, Rajesh, is not self-marked in the seed. With the rule on, most specs would first have to mark Rajesh's own attendance, and a class's check could pass on a reused self check instead of running. So a spec that is not about the rule runs with both off: the fixture's `selfFirst` option defaults to `false`, and `preset()` then patches the demo config after the preset (`selfFirstOff` in `fixtures.ts`: `selfBeforeStudents: false`, `selfPassReuseMinutes: 0`). A spec about the rule opts in with `test.use({ selfFirst: true })` (`self-first.spec.ts`, `voice-self-first.spec.ts`). The patch merges into the stored demo state through the controller's state repository, not `setConfig`, so the demo's `presetId` stays set and a story recognised by its preset (the First-time story in `login-assist.spec.ts`) is still the one tested. Unit and integration tests do the same through `SELF_FIRST_OFF` in `tests/helpers/app.ts` (`setup()` merges it under every override); a test about the rule passes `staff: { selfBeforeStudents: true }`.

Helpers in `fixtures.ts`:

- `preset(page, id)` opens `/?preset=id`, waits for Home, and turns own attendance first off unless the spec opted in.
- `demo(page, "setConfig({...})")` calls the demo controller.
- `nav(page, 'Reports')` finds the bottom-nav link.
- `realGreeting(name, language)` is the Home greeting for the machine's real time of day (D-151), computed by the test from the IST clock and matching either side of a boundary up to two minutes away. In service tests, `setup(overrides, { wallClock })` injects the wall clock the greeting reads; without it the greeting shares the fixed 10:15 clock.
- `expectNoOverflow(page)` and `expectGroupsFit(page)` are the layout checks.

## Visual QA against the prototype

Visual fidelity was checked by screenshot, not by pixel diff (the prototype has a fake phone frame and status bar):

1. Capture the prototype screens with Playwright (`prototype/Prototype.html`, driving its own controls), and the app screens at 360px and 320px from the production build.
2. Compose side-by-side sheets (prototype left, app right), review them screen by screen, and fix the drift. Remaining differences are the deliberate ones listed in `DECISIONS.md`, among them the removed _Submit attendance?_ sheet on Review (D-149), the removed Today/Yesterday switch on the principal's record (D-150), and the Students | Staff switch in the white top band instead of the scroller (D-159).
3. Run a multi-lens design critique (prototype fidelity, SwiftChat DS, impeccable, design-taste-frontend, huashu-design, accessibility, field UX, Marathi). The prototype and DS stayed authoritative over the lenses. The critique found 82 findings, about 38 distinct issues after de-duplication. Most are fixed; D-037 to D-044 record the design calls, and D-044 lists what was deliberately left open.

The round-2 consistency pass (D-159) repeated this as an audit of the app itself: every screen captured at four sizes in English and Marathi, with contact sheets, then audited and adversarially verified (19 findings confirmed, 8 rejected as prototype or decision). The fixes are guarded by the U-numbered E2E tests above.

When changing UI, run `npm run e2e` and look at the changed screens at 320px, 360px and 1280px (DevTools device mode is enough).

### The detection path with a real face

Chromium's fake camera shows a test pattern with no face, so E2E proves only that detection starts and asks for a face. The full detection-driven registration (straight → left → right) was checked once by hand. Chromium was fed a synthetic head-turn video built from renders of a public-domain portrait, through `--use-file-for-fake-video-capture`. That media was kept in the session scratch folder and deleted; it is **not** in this repository and must not be added as a fixture.

That run confirmed three things:
- the frontal photo is taken after about 0.5 s;
- turns are accepted from the measured yaw ratios (about ±0.24 to ±0.30 at 22–30°);
- a person who turns the "wrong" way first is still accepted after the 1.5 s mirror calibration.

It also led to lowering the turn threshold from 0.22 to 0.18 (D-048). Re-check on a real phone before rollout.

## Writing new tests

- Test a rule in `src/domain` with a unit test, and test a service flow through `createMockContainer` in the integration suite. Build the setup with `setup()` / `signIn()` in `services.test.ts`.
- Use `FixedClock(instantAt('2026-09-25', 'HH:MM'))` for time-dependent behaviour; never depend on the real clock. A greeting reads the wall clock: inject it with `setup(overrides, { wallClock })`, and in E2E match it with `realGreeting()`.
- A new spec or service test about classes runs with own attendance first off by default; opt in (`test.use({ selfFirst: true })`, or `staff: { selfBeforeStudents: true }`) only when the rule is what it tests.
- E2E: prefer role and name locators (`getByRole('combobox', { name: 'Attendance for Aarav Pawar' })`, then `selectOption('absent')`). An inactive (`aria-disabled`) button such as Review & Submit with gaps, or Sync now offline, needs `click({ force: true })`: it still explains itself. Copy is the contract, so if you change an English string, update the spec.
